## Problem Statement

A personal library of 30-90 second exercise tutorials, grouped by muscle group, that you can pull up on your phone **in the gym, between sets, with no signal**.

The clips are reels saved from Instagram, TikTok and YouTube Shorts. You already download them to phone storage yourself. Today you find them through the social apps' saved collections or the phone gallery, and two things break:

- **"Signal is bad"**: in the gym, streamed reels buffer or don't load.
- **"Lists become too cumbersome"**: scrolling a long list or collection between sets takes too long.

## What Makes This Cool

- **No list on the gym floor.** Before training, tick today's groups (say Glutes + Quads). The app becomes a full-screen swipe deck of only those clips. Each loops on mute, the screen stays on, swipe up for the next exercise.
- **The tutorial is your rest timer.** Tap "Set done": a countdown runs over the looping clip and the phone buzzes when rest is over. You don't need a separate timer app.
- **Loop only the movement.** At home you can mark the 5 seconds of the actual rep and skip the creator's intro and talking. In the gym only that part loops.
- **Nothing leaves the phone.** No account, no server, no subscription, and it works in airplane mode.

## Constraints

- **Android phone, Chrome.** One user, personal use only.
- **Zero signal in the gym**, so every video must already be on the device.
- **Clips are 30-90 s**, roughly 5-40 MB each. Expect 50-150 clips, about 1-3 GB in total.
- **Clips come from social apps but arrive as files.** You download them to phone storage outside this app.
- **Videos are third-party content.** The library is private and never republished.

## Premises (agreed)

1. **The phone is the library.** Videos are copied into the app's on-device storage and play with zero signal. v1 has no server, account or login.
2. **It is an installed web app**, using Chrome's "Install app", not a Play Store app. A free static host serves the code; after the first load the app runs offline.
3. **Adding clips uses a multi-select file picker only.** *(Revised after the second opinion: the Android Share menu moves to "later". Instagram and TikTok share a link, not the file, so share-into-app would only help from the Gallery.)*
4. **Each clip has one main muscle group plus optional extra groups.** A Bulgarian split squat then appears under both Glutes and Quads. Groups come from a starter list you can rename or add to.
5. **Workout mode is the main gym screen.** Browsing the full library is for home.
6. **Backup is a small export file and is required.** Your original videos stay in the phone gallery or Google Photos. The app exports a metadata file (clip names, groups, trims, rest times, order, plus group names and settings), so a wiped app can be rebuilt by picking the same files again. Each clip takes about 2x space on the phone, which is accepted.

## Approaches Considered

- **A: Lean offline library.** Library, Add and Workout deck screens plus JSON backup (human: ~2-3 days / CC: ~1-2 hrs). Not chosen: it loops whole clips, creator talking included, and still needs a separate timer app.
- **B: Gym-floor deck. CHOSEN.** A plus an optional rep-loop trim and a rest timer with vibration (human: ~4-5 days / CC: ~3-4 hrs).
- **C: Offline app + cloud sync.** A backend holds the master copy and adds login and laptop editing (human: ~1-2 weeks / CC: ~1 day). Not chosen: it breaks premise #1 and spends most of the effort on backup rather than on the gym moment.

## Recommended Approach: B, Gym-floor deck

### Wireframe

The approved sketch is in [gym-floor-deck-sketch.html](gym-floor-deck-sketch.html), with a screenshot at `docs/designs/gym-floor-deck-sketch.jpg`. It has three screens: Library, Add clips and Workout deck.

### Stack

- **Vite + TypeScript + Preact.** Vanilla TS also works; the UI is small.
- **vite-plugin-pwa** for the manifest and a service worker that precaches the app shell, so the app cold-starts offline.
- **Dexie** (an IndexedDB wrapper) for all data, video blobs included.
- **Browser features, no libraries:** `<video muted loop playsinline>`, CSS scroll-snap, Screen Wake Lock, `navigator.vibrate`, `requestVideoFrameCallback`, `navigator.storage.persist()` / `estimate()`.

### Data model (Dexie tables)

- **Ids:** clip and group ids are UUID strings (`crypto.randomUUID()`), never auto-increment, so restored ids can't collide with clips added during a restore.
- **`clips`**
  - Identity and display: `id`, `name`, `mainGroupId`, `extraGroupIds[]`, `order`, `createdAt`
  - Video: `video` (Blob), `mime`, `durationSec`, `sizeBytes`, `thumb` (JPEG Blob)
  - Rep loop and rest: `loopStart?`, `loopEnd?`, `restSec` (copied from `defaultRestSec` at import; changed only in Edit clip)
  - Restore matching: `sourceFileName` (tie-breaker only; the main match is `sizeBytes` + `durationSec`)
  - Order: `order` is set to the end of the list at import and never changes in v1. Reordering is a later feature.
- **`groups`**: `id`, `name`, `order`. Seeded with Chest, Back, Shoulders, Biceps, Triceps, Quads, Hamstrings, Glutes, Calves, Core, Cardio/Full body.
- **`settings`**: `defaultRestSec` (90, editable in Settings), `lastWorkoutGroupIds[]`, `persistGranted`.
- **`activeWorkout`** (one row, or empty when no workout is running): `groupIds[]`, `deckIndex`, `restEndsAt?`, `updatedAt`. It is written on every change, so a workout survives Android discarding the page or a reload.
- **`pendingRestore`** (one row, only while a restore is in progress): the imported manifest plus the ids of entries already matched.
- Schema changes go through Dexie version upgrades, so an app update never drops data.

### Screens

1. **Library (home).**
   - Group chips with counts, and a thumbnail grid filtered by chip.
   - A clip appears under its main group and under each extra group.
   - ✂ marks trimmed clips. Tap a thumbnail to open **Edit clip**.
   - The biggest button is **Start workout**. A gear icon in the top bar, next to "+ Add", opens Settings.
   - **First run / empty library:** an "Add your first clips" button and a "Restore from backup" link. The top bar with the gear stays visible, and Start workout is disabled.
   - **On launch:** if `activeWorkout` exists and its `updatedAt` is under 3 hours old, the app opens straight into the deck at the saved position, with any running rest still counting down. If it is older, the app clears it and opens the Library.
2. **Add clips (home).**
   - The picker allows multi-select (`accept="video/*" multiple`). You then step through the chosen clips one by one.
   - Required: name and main group. Optional: extra groups and the trim (two handles on a timeline, preview loops the selection).
   - Thumbnail: seek to 1 s and draw the frame to a canvas as JPEG.
   - The clip is saved on "Save & next".
3. **Edit clip (home).** Uses the same form as Add, for one existing clip: name, main and extra groups, trim, and rest seconds (`restSec`). It also has a **Delete** button with a confirm step; deleting removes the clip's video and thumbnail and frees the space. This is also how clips imported before the trim feature get trimmed.
4. **Workout deck (gym).**
   - **Start:** a group picker opens with last time's groups pre-ticked. Each group shows its clip count. The start button is disabled while the ticked groups hold 0 clips.
   - **Deck contents and order:**
     - Each clip appears **once**, even if it belongs to two ticked groups.
     - A clip is placed under the first ticked group (in group order) that is its main group. If none of the ticked groups is its main group, it goes under its first ticked extra group.
     - Within a group, clips sort by `order`.
   - **Playback:** each clip plays muted and looped, either the trimmed segment or the whole clip.
   - **Rest timer:**
     - "Set done → start rest" starts a countdown of the current clip's `restSec`. Tapping it again while a rest is running restarts the countdown.
     - There is one rest overlay for the whole deck, and it stays on screen while you swipe between clips.
     - "+15s" extends only the current rest; it doesn't change `restSec`.
     - At zero the overlay reads "Rest over" and the phone vibrates. The deck does **not** advance by itself.
     - Tapping the overlay dismisses "Rest over" and clears `restEndsAt`. Tapping "Set done" in any state starts a new `restSec` countdown, dismissing "Rest over" if it is showing.
     - If the app resumes after `restEndsAt` has already passed, the overlay shows "Rest over" without vibrating.
   - **Navigation:** swipe up for the next exercise. "✕ End" clears `activeWorkout` and goes back to the Library. Android's back gesture also goes to the Library, but keeps `activeWorkout` and shows a "Resume workout" bar there (eng review R1).5. **Settings.**
   - Add, rename and reorder groups. (Adding was approved in office hours D6 and restored by the eng review.)
   - Default rest seconds (`defaultRestSec`).
   - Storage used and available.
   - Persistence status.
   - **Export backup** downloads a JSON manifest:
     - Top level: `{version, exportedAt, groups[{id, name, order}], settings{defaultRestSec}, clips[...]}`
     - Each clip: `{id, name, mainGroupId, extraGroupIds, order, loopStart, loopEnd, restSec, sourceFileName, sizeBytes, durationSec}`
   - **Restore** can start only when the library has no clips. It can be continued while a `pendingRestore` exists.
     - **Start:** pick the manifest. It is saved as `pendingRestore`, so the restore survives Android discarding the page while the system picker is open.
     - **Groups and settings first:** the groups table and `settings.defaultRestSec` are replaced with the manifest's values.
     - **Videos:** pick them over as many rounds as you like. Each picked file is matched to a manifest entry and re-imported. It keeps its manifest `id`, `order`, group ids, trims and `restSec`.
     - **Finish:** `pendingRestore` is cleared when every entry is matched or you tap Finish. Unmatched entries are then dropped.
6. **Routing (all screens, eng review R1).** Each screen is a hash route: `#/library`, `#/add`, `#/edit/<id>`, `#/workout`, `#/settings`. System back goes to the previous screen, and back from Add/Edit acts as Cancel.

### Behaviour details and edge cases

- **Offline:** the service worker precaches the app shell. All video comes from IndexedDB. After install, the only network traffic is the service worker's update check, and only when the phone is online.
- **Updates never interrupt a workout:** set vite-plugin-pwa to `registerType: 'prompt'`. A new version shows an "Update available" button in Settings and never reloads the page on its own.
- **Persistence:** call `navigator.storage.persist()` on the first import. If Chrome denies it, show a standing banner: "Chrome may clear videos when space runs low. Export a backup."
- **Storage full:** catch `QuotaExceededError` on save and show used/available space from `storage.estimate()`. Refuse that clip and keep the ones already saved.
- **Unplayable video** (for example an HEVC file the phone can't decode): `loadedmetadata` alone doesn't prove a clip plays, because a file whose video track can't be decoded can still fire it and then show no picture. A clip counts as playable only if the thumbnail step succeeds within 5 s:
  - `seeked` fires at 1 s,
  - `videoWidth > 0`, and
  - `drawImage` produces a non-empty JPEG.

  Otherwise reject the clip with a clear message instead of saving a dead entry.
- **Duplicates:** warn when `sizeBytes` matches an existing clip and `durationSec` is within 0.1 s. The file name is only a tie-breaker.
- **Loop precision:** check the loop end with `requestVideoFrameCallback`, which is frame-accurate. `timeupdate` is only accurate to about 250 ms and would show a flash of the next rep. When the loop end is reached, seek back to `loopStart`.
- **Loop seam:** seeking to a `loopStart` that isn't a keyframe can cause a brief stall at every loop. A small hitch is acceptable in v1. If it's bad on the phone, the fallback is two alternating `<video>` elements, each pre-seeked to `loopStart`.
- **Memory:** an IntersectionObserver plays only the visible clip. Object URLs exist only for the current clip and the ones either side; all others are revoked.
- **Wake lock:** take a screen wake lock in Workout mode. Android releases it when the tab is hidden, so request it again on `visibilitychange`.
- **Timer accuracy:**
  - The countdown is computed from `activeWorkout.restEndsAt`, a timestamp stored in IndexedDB, not by counting ticks, so it doesn't drift.
  - It stays correct if you switch away from the app and come back, even if Android discarded the page in the meantime.
  - In v1 the buzz only fires while the app is on screen. Workout mode keeps the screen on, so that is the expected case.
- **Restore:**
  - Clips are matched by `sizeBytes` + `durationSec`, with the file name as a tie-breaker. Android's Photo Picker can report different file names than the Files picker, so the name can't be the main key.
  - Unmatched manifest entries are listed so you can pick their files by hand.
  - A video you deleted everywhere cannot be restored.

## Open Questions

- **Deck order.** v1 uses group order, then library order. Are saved routines ("Leg day A", in a fixed order) needed after a few weeks of use?
- **Default rest.** 90 s globally, remembered per clip. Is that right for your training?
- **Deleting gallery originals to save space.** The metadata-only backup could then no longer restore videos. If that matters, add a full export (a zip of the videos) later, or go to Approach C.
- **Share from Gallery.** Run a 10-minute stub test of `share_target` on your phone before adding it.

## Success Criteria

- **Speed:** from unlocking the phone to today's first clip looping takes **under 5 seconds**, in airplane mode.
- **Offline cold start:** import 50 real clips, kill the app, turn on airplane mode and cold-launch. Every clip plays and trims are respected.
- **Real workout:** a full 6-exercise session using only the deck, with no trips to the gallery or Instagram and no separate timer app.
- **Restore:** export, clear the site's data in Chrome, then restore from the manifest plus re-picked files. Names, groups, trims and rest times come back.
- **Still useful:** you are still opening it at the gym 4 weeks later.

## Distribution Plan

- **Hosting:** a static build on Cloudflare Pages or GitHub Pages (free, HTTPS, which the service worker requires). Deploy runs on push once the folder is a git repo; no CI beyond the host's build step.
- **Install:** open the URL once in Chrome on the phone and tap "Install app".
- **Updates:** an online launch downloads any new version in the background. It is applied when you tap "Update available" in Settings, or after the app is fully closed. Data lives in IndexedDB and survives updates.
- **Privacy:** the URL is public but holds no data. Every browser that opens it gets its own empty library, and no secrets ship in the build.
